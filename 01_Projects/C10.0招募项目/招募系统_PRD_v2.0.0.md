# 招募系统 PRD

## 一、摘要

本 PRD 定义招募系统的实现范围与需求规格,是 v1.0.0 依据《10.0 面聊流程优化 V2》全面升级后的版本。系统为自建替代原有高成本第三方招募系统,覆盖候选人从**推荐/报名到通过新生见面会**的 10.0 全流程管理,并将招募从「靠人推动」升级为「流程标准化 + 数据沉淀 + AI 辅助决策」的闭环体系。

与 v1.0.0 相比,v2.0.0 的核心变化:

1. **流程升级为 10.0 二十步闭环**——新增「推荐 → 统一入口 → 结构化报名 → AI 初筛 → AI 画像匹配/风险评分 → 人工复核 → 进入面聊池」前置链路,及「申诉管理 → 立方有约 → AI 花名审核 → 新生见面会 → 数据沉淀反哺」收尾链路;
2. **模块从 8 个扩展至 15 个**——新增 AI 初筛引擎、动态面聊专家库、申诉管理、AI 花名审核、人才回流库、推荐人画像、数据沉淀与分析等模块;
3. **确立 AI 介入宪法**——**AI 永远作为建议方,不自动裁决**;所有「拦截/退回」均为 AI 标记 + 人工确认后生效;AI 初评综合分仅供面聊官参考,不决定录不录(2026-09-05 拍板);
4. **角色从四类扩展至五类**——新增推荐人角色,面聊组长升级为面聊官(动态专家库),并支持申诉复核组、面聊教练等子角色;
5. **关注指标从「只关注数量」转为关注质量、同频度、退出率**,全过程数据沉淀,反哺下一轮招募画像。

## 二、背景

- 现有第三方招募系统因费用过高被弃用,业务方决定自建替代系统;
- 9.0 招募全流程 SOP 与投票判定规则已定稿并沉淀经验,候选人和历史数据不迁移,首批候选人通过表单填写导入;
- **10.0 招募不是简单把 9.0 流程再跑一遍**,而是借 9.0 的真实经验,重点解决:简历质量参差不齐、临时找面聊官、面聊结果靠人工经验、申诉无门槛、花名审核耗费人力、只关注招募数量、招完就结束等 7 大问题;
- 2026-09-05 与业务方完成关键拍板:① AI 初筛**只标记不拦截**(守宪法:AI 永远建议方,人工确认后生效);② AI 初评**给综合参考分且面聊官可见**(V2 口径),但不决定录不录;③ 本系统按 **10.0 专属**口径命名与实现(C10.0 展示、20 步闭环流程);
- 推荐人激励(银币奖励)在系统外处理;立方有约、新生见面会为线下环节,系统仅提供标记与展示。

## 五、角色权限

| 角色 | 权限范围 | 说明 |
|---|---|---|
| 管理员 | 全部权限 | 应用最高权限,所有记录可查/编辑/删除,可修改应用配置;可指定申诉复核组成员、花名确认人 |
| 运营者 | 读写权限(不含底层配置) | 可查看、编辑所有记录;执行 AI 标记的人工复核确认、花名风险人工确认、综合判断、立方有约/新生见面会标记 |

| 面聊官(含场次主持人/教练) | 面聊相关权限 | 可查看被分配场次的候选人材料(含 AI 参考分与风险标签)、提交结构化评分与投票;教练可查看带教对象校准反馈 |
| 推荐人 | 推荐入口权限 | 提交推荐与查看候选人结果通知(进入面聊池/退回补充/拦截/通过);查看本人推荐人画像 |

子角色说明(不新增角色位,以权限标记区分):

- **申诉复核组**:由管理员从运营者/城市负责人中指定,负责申诉复核与改判;
- **花名确认人**:运营者或其指定人,负责 AI 花名风险项的最终确认;
- **面聊教练**:面聊官子角色,由 8.0/9.0 资深同学担任,负责支援 10.0 全程并带教新面聊官。

## 七、功能需求详情

### 7.1 驾驶舱 — 招募进展概览看板(P0)

**功能描述**
展示招募全局看板,提供整体招募进展数据总览,让管理者实时掌握 10.0 招募全局进度。

**功能点**

| 功能点 | 说明 |
|---|---|
| 总候选人数量统计 | 显示系统内全部候选人总数(按推荐/报名口径) |
| 各环节流转人数 | 按「报名 → AI初筛 → 人工复核 → 面聊池 → 前台面聊 → 中台面聊 → 综合判断 → 立方有约 → 花名审核 → 新生见面会」展示各环节当前人数 |
| 漏斗转化统计 | 各环节通过率、整体通过率;含 AI 标记建议拦截数、退回补充数、记风险放行数 |
| 通过率/退出率 | 综合判断通过率、退出率(按退出原因编码分布) |
| 各城市进展看板 | 按城市维度展示候选人数量、面聊完成率、专家库覆盖 |
| 各小组/场次进展看板 | 按面聊场次维度展示面聊完成情况、评分提交率 |
| 推荐人维度统计 | 推荐人排行、推荐质量、被拦截/退回占比、推荐人池健康度(新增) |
| 专家库使用统计 | 面聊官接单量、场次覆盖、教练带教进度(新增) |
| AI 运行统计 | AI 初筛处理量、花名查重量、反馈表生成成功率、AI 标记人工采纳率(新增) |

**数据来源**:候选人管理模块、面聊与结构化评分、申诉管理、花名审核、推荐人画像等模块数据。
**交互说明**:页面加载自动刷新;支持按城市、环节、届期筛选(当前届期固定 10.0);点击数据项可下钻到对应候选人列表。

### 7.2 候选人管理(P0)

**功能描述**
候选人全流程信息集中管理,从推荐/报名到新生见面会的各环节记录、评分、判定结果统一追踪。

**功能点**

| 功能点 | 说明 |
|---|---|
| 候选人列表 | 表格展示:基本信息、推荐人、城市归属、角色标签、当前环节、AI 风险/评分标签、面聊记录、最终状态 |
| 基本信息管理 | 姓名、联系方式、报名时间、推荐人、简历文件(上传/预览) |
| 结构化报名信息 | 报名表单按结构化字段收集(关键字段必填,供完整度校验) |
| 面聊池状态 | 通过人工复核后进入面聊池,带风险标签(记风险放行)的候选人标黄 |
| 城市归属 | 报名后系统自动匹配城市(按表单信息),支持手动调整 |
| 角色标签 | 按报名时间节点自动判定:发起人/候选人 |
| AI 评分与风险标签 | 展示 AI 初评综合分、完整度/质量/画像风险标记(均带「待人工确认/已确认」状态) |
| 当前流程环节 | 显示候选人当前所处 10.0 SOP 环节及状态 |
| 申诉与回流标识 | 申诉中/已申诉、回流候选人标识(人才回流库来源) |
| 筛选与搜索 | 支持按城市、角色、环节、状态、推荐人、风险标签筛选;支持关键词搜索 |
| 首批导入 | 首批候选人通过表单填写导入(excel/csv 格式,含推荐人字段) |

**数据流转**:推荐信息/报名信息自动写入 → AI 初筛标记 → 人工复核 → 进入面聊池 → 城市匹配 → 分流 → 面聊 → 综合判断 → 申诉/立方有约 → 花名审核 → 新生见面会。
**页面交互要素**:候选人详情页聚合显示基本信息、简历、AI 初筛报告、环节流转时间线、各场面聊记录、评分与投票结果、申诉记录;状态标签用颜色区分(待初筛/待复核/面聊池/面聊中/已通过/已退出/申诉中)。

### 7.3 AI 初筛引擎(P0,新增)

**功能描述**
在人工复核前,由 AI 对结构化报名信息与简历做标准化初筛,**仅产出标记与参考分,不做任何状态变更**;所有拦截/退回动作须由运营者人工确认后生效(2026-09-05 拍板:AI 只标记不拦截)。

**功能点**

| 功能点 | 说明 |
|---|---|
| 简历信息完整度校验 | 自动检查关键字段是否为空、简历是否过于简单(字数/结构化程度);输出完整度评分与缺失清单 |
| 简历质量分级 | 按信息丰富度、结构化程度对简历分档(如 A/B/C 档),供人工复核排序 |
| 基础资格标记 | 对「基础条件明显不符合(如学历、在读状态等客观门槛)」输出**建议拦截标记**,由人工确认后拦截并返回推荐人 |
| 画像匹配度评估 | 对候选人进行招募画像匹配评估,匹配度较低时**记风险标签**,不直接淘汰 |
| 风险原因编码 | 所有标记携带编码(字段为空/过于简单/资格不符/画像不匹配),便于统计与人工处理 |
| 复核队列 | 汇总所有 AI 标记项,供运营者逐项或批量确认(批量确认需二次确认并填写原因) |
| 复核动作 | 人工确认后可执行:①通过 → 进入面聊池;②退回补充 → 通知候选人/推荐人补充后重跑初筛;③拦截 → 通知推荐人;④记风险放行 → 带标签进入面聊池 |
| 三次不合格建议放弃 | 同一候选人累计 3 次退回补充后仍不合格 → 系统建议推荐人放弃,进入观察名单(口径待运营确认,见 TBD-06) |
| AI 初评综合分 | AI 从 基础资格 + 信息完整度 + 招募画像匹配度 + 经历质量 + 主动性信号 五个维度给出参考分;分数对面聊官可见,仅供面聊前聚焦参考,**不决定录不录** |
| 初筛报告 | 自动生成结构化初筛报告(AI 标记明细 + 评分依据),人工复核时可编辑批注 |
| 可解释性 | 每项标记与评分附依据摘要(命中字段/关键证据),避免黑盒 |
| 开关与降级 | AI 服务不可用时切换人工初筛队列(降级模式),不阻断流程 |

**边界说明**:AI 不自动进入面聊池、不自动退回、不自动拦截、不自动淘汰——所有影响候选人状态的输出均需人工确认。

### 7.4 动态面聊专家库(P1,新增)

**功能描述**
将 8.0/9.0 校友中有意愿、有能力担任面聊工作的同学沉淀为动态专家库(区分前台面聊/中台面聊、按城市组织),系统依据多维画像**直接推荐适合的面聊官**,再由人工敲定时间,替代「临时找面聊官」。

**功能点**

| 功能点 | 说明 |
|---|---|

### 7.7 全流程自动流转引擎(P0)

**功能描述**
按 10.0 招募 SOP 自动推进候选人状态,实现招募流程全链路自动化。

**10.0 流程定义(已定稿 SOP,二十步闭环)**

```
① 推荐人 → ② 统一入口/海报 → ③ 结构化报名 → ④ AI 基础资格筛选(标记)
→ ⑤ AI 画像匹配 + 风险评分(标记) → ⑥ 人工复核 → ⑦ 自动匹配城市
→ ⑧ 发起人/候选人分流 → ⑨ 系统匹配面聊专家池面聊官(人工敲定时间)
→ ⑩ 前台面聊 → ⑪ 结构化评分 → ⑫ 中台面聊 → ⑬ 综合判断
→ ⑭ 正常通过 / 淘汰 → ⑮ 符合条件才进入申诉流程 → ⑯ 申诉复核
→ ⑰ 立方有约(线下) → ⑱ 花名审核(AI 为主 + 人工辅助) → ⑲ 新生见面会
→ ⑳ 全过程数据沉淀 → AI 分析 → 反哺下一轮招募
```

**状态流转规则**

| 当前环节 | 触发条件 | 下一环节 |
|---|---|---|
| 报名完成 | 系统自动 | AI 初筛(AI 标记产出) |
| AI 初筛完成 | 产生标记与参考分 | 人工复核 |
| 人工复核通过 | 运营者确认 | 进入面聊池 |
| 人工复核退回/拦截 | 运营者确认 | 退回补充(通知推荐人)/拦截(通知推荐人,退出) |
| 面聊池 | 系统自动 | 城市匹配(自动) |
| 城市匹配完成 | 匹配成功 | 发起人/候选人分流(按时间节点) |
| 分流完成 | 系统按时间规则判定 | 系统推荐面聊官(专家库) |
| 面聊官敲定 | 人工确认场次时间 | 前台面聊 |
| 前台面聊通过 | 结构化评分 + 投票判定 = 通过 | 中台面聊 |
| 中台面聊通过 | 结构化评分 + 投票判定 = 通过 | 综合判断 |
| 综合判断完成 | 运营者确认 | 正常通过 / 淘汰 |
| 正常通过 | 系统自动 | 立方有约(线下,系统标记) |
| 立方有约完成 | 运营者标记 | 花名审核(AI 查重 → 人工确认) |
| 花名审核通过 | 人工确认无风险 | 新生见面会(线下,系统标记) |
| 新生见面会完成 | 运营者标记 | 正式通过 → 进入 C10.0 展示名单 → 数据沉淀 |
| 淘汰(符合申诉条件) | 系统按准入条件校验 | 申诉流程 |
| 申诉复核通过 | 申诉复核组确认 | 回到综合判断通过态(改判) |
| 申诉复核驳回 | 申诉复核组确认 | 维持淘汰(退出) |

**异常流转**

| 场景 | 处理方式 |
|---|---|
| 任一环节人工确认为「不通过」 | 标记退出流程,记录退出原因编码(红线/资格不符/面聊不通过/主动退出等) |
| AI 标记退回补充超 3 次 | 系统建议推荐人放弃,进入观察名单(口径见 TBD-06) |
| 城市匹配失败 | 标记「待分配」,人工干预 |
| 专家库无匹配面聊官 | 标记「待分配小组」,通知管理员与城市负责人 |
| 淘汰但不符合申诉条件 | 直接退出,系统提示不满足的准入条件 |
| 退出流程的候选人 | 不可通过普通流程重新进入;非红线原因者可经人才回流库单独流程回流 |

## 八、系统规则

### 8.1 角色判定规则(发起人/候选人分流)
- 以运营方设定的时间节点为界,之前报名的归属为「发起人」,之后报名的归属为「候选人」;
- 角色判定后不可手动更改(除非管理员介入,高危操作)。

### 8.2 城市匹配规则
- 候选人报名时填写城市信息,系统自动匹配到对应城市;
- 匹配失败时标记为「待分配」,由运营者手动分配。

### 8.3 AI 介入规则(2026-09-05 拍板)
- **AI 永远建议方,不自动裁决**:AI 产出的一切标记、评分、预警均为「建议/参考」,不直接变更候选人状态;
- **拦截/退回守宪法**:基础条件明显不符合、关键字段为空等,均由 AI 标记「建议拦截/建议退回」,**人工一键确认后**才生效并通知推荐人;画像匹配度较低仅记风险,不淘汰;
- **AI 初评综合分口径(V2)**:AI 从基础资格、信息完整度、招募画像匹配度、经历质量、主动性信号五维度给参考分,面聊官可见,用于面聊前聚焦;**AI 不决定录不录**,每一张票与每一次判定都是人做出的;
- AI 输出留痕:每次 AI 产出记录模型版本、输入摘要、输出明细,可追溯;
- AI 服务异常时降级为人工队列,不阻断流程。

### 8.4 简历初筛门槛规则
| 情形 | AI 动作 | 人工动作 |
|---|---|---|
| 关键字段为空 | 标记「信息不完整」 | 确认后返回补充(不能进入面聊池) |
| 简历过于简单 | 标记「质量过低,建议补充」 | 确认后返回补充 |

### 8.5 面聊判定规则
- **投票判定规则(沿用已定稿,系统固化)**:满 4 票自动判定,第 5 票起不计入;仅 3 票且面聊人数 = 3 → 自动判定;不足 3 票,或 3 票但面聊人数 > 3 → 不做判定,标记「待判定」;
- 前台/中台通过条件:1/2 通过且无 1/3 反对(按场次角色判定);
- **综合判断(10.0 新增)**:综合前台结构化评分、中台结构化评分、AI 初评参考分与投票结果,由运营者执行最终判断;结构化评分与投票明细进入决策档案;
- 判定结果不可撤回(管理员可手动修正异常情况,高危操作,需填写原因)。

### 8.6 申诉准入规则
- 可申诉情形(满足其一即可):① 面聊人数不足;② 存在明显信息遗漏;③ 面聊结果存在明显冲突;④ 有新的重要信息补充;

- 准入校验为硬门禁,不符合条件直接驳回并提示原因;申诉有明确门槛,不做无边界内耗。

### 8.7 花名审核规则
- AI 三重查重:字面重复、语义重复、关联人物重复(人名与其字号重复等);
- 红线规则(不可自创/政治宗教/在世人物/角色唯一)命中 → 红色风险,建议修改;
- 风险项由人工最终确认;审核记录不可删除仅可追加。

### 8.8 专家库推荐规则

### 8.9 流程流转规则
- 状态变更需记录操作人、操作时间、变更前状态、变更后状态、原因;

- 流转引擎状态与候选人状态保持最终一致。

### 8.10 数据访问规则
- 城市负责人只能编辑自己城市归属的数据;
